# LYNXgwas — Session Update (2026-07-07)

This document summarizes the work done in this session: what changed, why, and how.

## 1. Reference panel fixes

### 1.1 NaN values in LD matrices
**Problem:** After replacing the AMR reference panel with a denser version, LD computations for `hisp` produced `NaN` values.
**Cause:** The new panel had only 347 samples, and 61.5% of variants in the test window were monomorphic (no variation) — PLINK can't compute r² for a monomorphic variant.
**Fix:** MAF-filtered the reference panel to keep only variants with minor allele frequency ≥ 1%, removing the monomorphic sites that produced NaN.

### 1.2 Duplicate variant IDs breaking `--clump`
**Problem:** `eurfin` locus identification returned 0 loci for every chromosome, with PLINK `--clump` failing with exit code 3 ("Duplicate ID").
**Cause:** Two separate issues in the reference panel `.bim` files (`refpanels/eur`, `refpanels/eas`, `refpanels/amr`):
1. Literal `.` placeholder variant IDs (tens of thousands of rows) — PLINK's `--clump` treats any duplicate ID as fatal, whereas `--r2` only warns.
2. True duplicate real rsIDs (e.g. `rs112108829`) from multi-allelic sites, which is a second, distinct source of duplication.

**Fix:**
- Rewrote all `.` placeholder IDs to `chr:pos`.
- Rewrote any ID occurring 2+ times (real duplicate rsIDs) to `chr:pos:a1:a2` so every row has a unique ID.

Diagnosed both issues via direct manual PLINK test runs against a minimal assoc file, isolating the panel as the root cause rather than the pipeline code.

## 2. Reference panel strategy changes

- Switched the **`hisp`** project to use the Hispanic cohort's own genotype data (`refpanels/hisp/Hispanic`, 8,519 samples) as its LD/locus reference panel instead of 1000 Genomes AMR — the study's own genotypes are a better-matched LD reference than a generic super-population panel.
- Extended this to all Hispanic-derived cohorts: **`hispchi`**, **`hispeurfin`**, **`hispeurfinchi`** now also use the Hispanic panel.
- Left other projects on their existing designated panels: **`eurfin`** → EUR, **`wang`** → EAS.
- Re-ran **Get Loci** + full **reprocessing** for all 6 projects under the new panel configuration.

## 3. Config bug fix — `wang`

Found while building the cross-file rsID lookup: `wang/config.properties` had `col.rsid=markername`, but the `markername` column actually holds `chr:pos:allele:allele` identifiers, not real rsIDs. The real rsID column was `snpid` (e.g. `rs4475691`).
**Fix:** `col.rsid=markername` → `col.rsid=snpid`, and `col.varid=` → `col.varid=markername` (so the chr:pos:allele:allele data is preserved under the correct field).

## 4. rsID recovery pipeline — three-strategy system

Ran "Add rsIDs" for all 6 projects and built out the recovery pipeline into three sequential strategies:

1. **Local dbSNP lookup** (pre-existing) — HTSJDK tabix query against the local dbSNP VCF by chr:pos, matching alleles (forward and reverse-strand).
2. **NCBI / gnomAD live API completion** (pre-existing, previously off by default) — rate-limited batch queries against NCBI and gnomAD for anything strategy 1 missed.
3. **Cross-file GWAS lookup** (new — `src/rsid/CrossFileLookup.java`) — scans every project's GWAS summary file (including the current project's own file) for a genuine rsID column, builds a chr:pos → rsID index, and uses it to fill in anything still unmatched after strategies 1–2. Whatever remains unmatched after all three strategies goes to the cross-project "Missing rsIDs" list.

### Implementation notes
- `RsidPipeline.java`: extracted `patchLocusJsonsWithRsids()` into a reusable public static method (used by both the automated pipeline and the new manual-submit endpoint); added Step 5 ("Cross-file GWAS lookup") between API completion and final JSON patching; bumped `totalSteps` from 5 to 6.
- Fixed a latent bug where API-recovered rsIDs were patched into locus JSONs but never written back to `rsid_recovery_results.csv` — this would have made the Missing rsIDs list inaccurate. Both API- and cross-file-recovered rows are now persisted back to the CSV with a `match_reason` column (`api` / `cross_file`).
- `CrossFileLookup.java` is in package `rsid`, so it could not import the default-package `Config` class (Java forbids importing across the named/unnamed package boundary) — it uses its own minimal `.properties` file parser instead.
- Added `src\rsid\CrossFileLookup.java` to `build.bat`'s compile list.

## 5. "Missing rsIDs" UI feature

Added a cross-project view for SNPs that remain unresolved after all three recovery strategies, so a user can manually supply the correct rsID.

- New **"Missing rsIDs"** button in the toolbar (between Tools and +New project).
- `GET /api/missing-rsids` — scans every project's `rsid_recovery_results.csv`, returns a JSON list of unmatched SNPs (project, chr, pos, ea, nea, match reason, and — if available — a `pos_only_rsid` suggestion).
- `POST /api/submit-rsid` — accepts `{project_id, chr, pos, rsid}`, patches the relevant locus JSON files in place via `RsidPipeline.patchLocusJsonsWithRsids()`, and updates the CSV row.
- Frontend modal (`index.html`): scrollable table of missing SNPs with an editable rsID field per row; rows with a `pos_only_rsid` candidate are pre-filled with an amber "suggested, unverified" hint the user can accept or overwrite.

### Why the suggestion feature exists
Investigated a specific case (hispeurfinchi, chr17:44305371, allele `c`) that the user found on gnomAD's website but which the pipeline reported as missing. Root cause: dbSNP records this position as an indel (`CAAA→C`), while the GWAS file reports it as a simple SNP (`C/A`) — an allele-representation mismatch, not missing data. The local matcher had actually found this as a `pos_only_rsid` candidate but conservatively declined to auto-assign it (allele mismatch). This is why the UI now surfaces `pos_only_rsid` as an editable suggestion rather than silently discarding it.

### API completion — now on by default
Per user decision, the "Enable API completion (NCBI + gnomAD)" checkbox in the rsID recovery dialog is now **checked by default** (previously off), and its options panel is visible by default. This means every future project's "Add rsIDs" run automatically benefits from all three recovery strategies without the user needing to remember to enable it.
